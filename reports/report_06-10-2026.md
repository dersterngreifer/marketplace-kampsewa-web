# Report Permintaan Penyesuaian Alur Transaksi
**Tanggal**: 06-10-2026

**Konteks Kendala:**
Penyesuaian alur status transaksi agar tersinkronisasi antara Frontend (Mobile Apps) dan Backend (Web Dashboard Admin).
Penambahan fase **Pengambilan** untuk memperjelas status antara pesanan yang telah dikonfirmasi dan masa sewa yang sedang berjalan.

**Pembaruan yang dilakukan (Backend):**
1. **Penambahan Status Transaksi (Fase "Pengambilan"):**
   - Transaksi yang disetujui (dikonfirmasi/di-ACC Admin) statusnya kini diubah menjadi **"Pengambilan"** (diubah dari sebelumnya langsung "Aktif").
   
2. **Pembaruan Flow & Tab di Web Dashboard:**
   - **Tab Order Masuk (Pending):** Aksi "Terima Order" kini memperbarui `status_penyewaan` menjadi `"Pengambilan"`.
   - **(BARU) Tab Pengambilan:** Telah dibuatkan halaman dan tab baru **"Pengambilan"** (route `/pengambilan/{id_user}`) untuk pesanan yang menunggu barangnya diserahkan kepada penyewa. Tersedia aksi/tombol **"Serahkan"** untuk mengubah status menjadi `"Aktif"`. Tab navigasi telah ditambahkan di semua halaman manajemen transaksi.
   - **Tab Sewa Berlangsung (Aktif):** Tetap berfungsi memonitor pesanan yang berstatus `"Aktif"`.
   
3. **Penyelarasan API & Status "Belum Bayar":**
   - Diperbarui mapping status transaksi pada API (`TransaksiController@riwayatPesanan`).
   - `"Belum Bayar"`: Pesanan dengan status `"Pending"` dan pembayaran `"Belum lunas"`.
   - `"Pending"` (Menunggu Konfirmasi): Pesanan dengan status `"Pending"` dan pembayaran `"Lunas"`.
   - `"Pengambilan"`: Pesanan dengan status baru `"Pengambilan"`.
   - `"Berlangsung"`: Pesanan dengan status `"Aktif"`.

Seluruh penyesuaian telah dipastikan sesuai dengan alur UX aplikasi Mobile, memberikan kejelasan alur status secara konsisten.

# Report Pembaruan API Riwayat Transaksi
**Tanggal**: 06-10-2026

**Konteks Kendala:**
Dokumentasi detail endpoint API untuk frontend mobile app terkait penambahan state status **"Pengambilan"**.

**Endpoint API Riwayat Transaksi**
**URL:** `/api/riwayat`
**Method:** `GET`

**Query Parameters:**
- `id_user` (Integer, Required): ID pengguna aplikasi (Penyewa).
- `tipe_riwayat` atau `status` (String, Optional): Kategori status filter (`belum-bayar`, `pengambilan`, `berlangsung`, `selesai`, `dibatalkan`).

**Detail Mapping Logic (Backend) Terbaru:**
1. Jika `tipe_riwayat=belum-bayar` ➔ Mengambil `status_penyewaan` = **"Pending"**
2. Jika `tipe_riwayat=pengambilan` ➔ Mengambil `status_penyewaan` = **"Pengambilan"**.
3. Jika `tipe_riwayat=berlangsung` ➔ Mengambil `status_penyewaan` = **"Aktif"**.
4. Jika `tipe_riwayat=selesai` ➔ Mengambil `status_penyewaan` = **"Selesai"** atau **"Pengembalian"**.
5. Jika `tipe_riwayat=dibatalkan` ➔ Mengambil `status_penyewaan` = **"Dibatalkan"**.

# Report Perbaikan Bug Tampilan List Transaksi (Sewa Berlangsung & Selesai)
**Tanggal**: 06-10-2026

**Konteks Kendala:**
Terdapat *bug* pada halaman list transaksi (Sewa Berlangsung & Order Selesai) di mana jika satu pelanggan yang sama (nama user sama) melakukan lebih dari satu transaksi penyewaan secara terpisah (misalnya menyewa produk A, lalu beberapa jam kemudian menyewa produk B dengan transaksi baru), data transaksi yang muncul di list tabel hanya satu transaksi saja. Hal ini disebabkan karena pengelompokan data (*grouping*) di Backend salah menggunakan ID User Penyewa (`id_user_penyewa`).

**Pembaruan yang dilakukan (Backend):**
1. **Perbaikan Grouping Logic pada TransaksiMenuController:**
   - Telah dilakukan perbaikan pada *method* `sewaBerlangsung` dan `orderSelesai`.
   - Mengubah *key* filter duplikasi dari `isset($seenUsers[$item->id_user_penyewa])` menjadi `isset($seenOrders[$item->id_penyewaan])`.
   - Mengganti variabel penyimpanan pengecekan dari `$seenUsers` menjadi `$seenOrders`.
   - Begitu juga pada *method* `pengambilan` telah diselaraskan penamaan variabel *grouping*-nya menggunakan pengecekan ID Penyewaan.

**Dampak pada Frontend/UI:**
- **Tidak ada perubahan kode HTML/Blade atau struktur UI yang diperlukan dari sisi tim Frontend.**
- Tabel list transaksi kini secara otomatis akan menampilkan baris transaksi yang sesuai (bisa menampilkan 2 baris atau lebih untuk user yang sama jika user tersebut memang memiliki lebih dari 1 transaksi terpisah yang sedang berjalan/aktif). 

Status bug: **Resolved**.

# Report Penambahan Waktu Deadline pada API Riwayat
**Tanggal**: 06-10-2026

**Konteks Kendala:**
Tim Frontend Mobile App membutuhkan acuan data berupa timestamp yang pasti *(absolute time)* dari Backend agar bisa menampilkan perhitungan mundur waktu sisa penyewaan (*countdown timer*: hari, jam, menit) secara *real-time* kepada pelanggan.
Mengingat aturan pengembalian pada sistem (Backend) dikunci secara baku (harus dikembalikan maksimal pukul 21:00 pada `tanggal_selesai`), maka Backend harus menyuplai acuan waktu tersebut.

**Pembaruan yang dilakukan (Backend):**
1. **Penambahan Field pada API `/api/riwayat`:**
   - Ditambahkan field `tanggal_mulai` (Format: `YYYY-MM-DD HH:mm:ss`)
   - Ditambahkan field `tanggal_selesai` (Format: `YYYY-MM-DD HH:mm:ss`)
   - **(BARU)** Ditambahkan field `waktu_deadline_pengembalian` (Format: `YYYY-MM-DD 21:00:00`) yang merupakan hasil kombinasi dari `tanggal_selesai` dengan setelan waktu *hardcode* pukul 21:00.

**Cara Penggunaan bagi Tim Frontend Mobile:**
- Untuk membuat *timer countdown*, silakan kurangkan nilai dari string datetime pada field `waktu_deadline_pengembalian` dengan waktu lokal (*current time*) pada perangkat pengguna (atau waktu server, jika melakukan sinkronisasi waktu).
- Tampilkan *countdown* ini utamanya pada saat `status_transaksi` bernilai `"Berlangsung"`.
- Jika waktu perangkat melebihi `waktu_deadline_pengembalian`, aplikasi mobile bisa menampilkan status "Terlambat".

**Contoh Response Update:**
```json
{
  ...
  "status_transaksi": "Berlangsung",
  "metode": "Transfer",
  "tanggal_mulai": "2026-10-06 10:00:00",
  "tanggal_selesai": "2026-10-08 00:00:00",
  "waktu_deadline_pengembalian": "2026-10-08 21:00:00",
  "rekening_bank": "...",
  ...
}
```

Status permintaan update: **Selesai**.

# Report Permintaan Penambahan Data Keterlambatan & Denda pada API Riwayat
**Tanggal**: 06-10-2026

**Konteks Kendala:**
Untuk memberikan transparansi bagi penyewa di aplikasi mobile (Frontend), diperlukan tambahan indikator detail saat pesanan masuk dalam status melebihi batas waktu (keterlambatan). Daripada aplikasi menghitung manual yang rawan berbeda perhitungan dengan dashboard, perhitungan total denda harus langsung disuplai secara *real-time* dari Backend.

**Pembaruan yang dilakukan (Backend):**
1. **Perhitungan Denda Dinamis pada Endpoint `/api/riwayat`:**
   - Menyalin dan mengimplementasikan aturan perhitungan denda (*business logic*) yang sama persis dengan yang ada pada Dashboard Admin.
   - Perhitungan dilakukan khusus untuk pesanan berstatus **"Aktif"** (Berlangsung) atau **"Pengembalian"**.
2. **Penambahan 3 Field Baru pada Objek Transaksi JSON Response:**
   - `is_terlambat` (Boolean): Bernilai `true` jika batas deadline (pukul 21:00 pada *tanggal selesai*) telah terlewati oleh waktu server saat ini.
   - `durasi_terlambat` (String): Mengembalikan representasi durasi telat (Misal: `"2 Jam"` atau `"1 Hari 5 Jam"`). Nilainya `null` jika `is_terlambat` adalah `false`.
   - `nominal_denda` (Integer/Double): Mengembalikan akumulasi total tagihan denda keterlambatan (Misal: `45000`). Nilainya `null` jika `is_terlambat` adalah `false`.

**Contoh Response Update:**
```json
{
  ...
  "id_transaksi": 142,
  "status_transaksi": "Berlangsung",
  "waktu_deadline_pengembalian": "2026-10-08 21:00:00",
  "is_terlambat": true,
  "durasi_terlambat": "1 Hari 2 Jam",
  "nominal_denda": 45000,
  ...
}
```

**Dampak pada Frontend Mobile:**
Dengan ketersediaan data ini, tim Mobile App dapat langsung melakukan pengecekan `if (is_terlambat == true)`. Jika terbukti telat, aplikasi cukup me-render nilai `durasi_terlambat` dan `nominal_denda` tersebut ke dalam bentuk UI/Widget *badge* peringatan warna merah.

Status permintaan update: **Selesai**.
