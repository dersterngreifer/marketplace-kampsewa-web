## 1. Kabar Baiknya: Fitur Sudah Ada, Tidak Perlu Build dari Nol

### 1.1 Konsep Dasar

> **1 Feedback = 1 Percakapan (Chat Thread)**

Customer mengirim feedback (rating + keluhan/saran). Feedback tersebut otomatis menjadi **ruang chat**. Setelah itu Customer dan Admin bisa saling kirim pesan (chat) di dalam feedback tersebut, seperti chat WhatsApp, sampai selesai.

Contoh alur:
```
Customer kirim feedback  →  status: "Belum Dibalas"
                          (masuk ke dashboard Admin sebagai "Belum Dibalas")
Admin balas              →  status: berubah jadi "Dibalas"
Customer balas lagi       →  status tetap "Dibalas", notif ke Admin
Admin balas lagi          →  percakapan berlanjut
```

### 1.2 Yang Sudah Ada di Sisi Web (Referensi/Gambarannya)

| Lokasi | Isi |
|---|---|
| `/developer/dashboard/notification` | Halaman "Pusat Notifikasi" Admin. Berisi 3 tab/list: **Belum Dibalas**, **Feedback Reply (Dibalas)**, **Customer Membalas Lagi** |
| Modal Chat | Dialog chat dengan bubble pesan, kanan = Admin, kiri = Customer, ada label waktu & nama pengirim |
| Halaman Detail Pengguna (`/developer/dashboard/detail-pengguna/{id}`) | Riwayat chat read-only per customer |

**File referensi kodingan (bisa dibaca tim kalian):**
- Controller Web: `app/Http/Controllers/Developer/NotificationController.php`
- Controller API: `app/Http/Controllers/Api/FeedbackChatController.php`

| `kriteria` | ENUM | `Sangat Baik` / `Baik` / `Cukup` / `Kurang` / `Sangat Kurang` |
| `status` | ENUM | `Belum Dibalas` / `Dibalas` |
| `created_at`, `updated_at` | timestamp | — |

### 2.2 Tabel `feedback_messages` — isi chat

| Kolom | Tipe | Keterangan |
|---|---|---|
| `id` | bigint (PK) | ID pesan |
| `feedback_id` | bigint (FK → `feedback.id`) | Menunjuk ke percakapan mana |
| `sender_id` | bigint nullable (FK → `users.id`) | Siapa pengirimnya |

### 3.3 `GET /api/feedback/{id}/messages` — Ambil Isi Chat

Mengambil **seluruh riwayat pesan** dalam 1 percakapan, dari yang paling lama ke yang baru.

**Contoh Response (200 OK):**
```json
{
  "success": true,
  "message": "Data chat berhasil diambil.",
  "data": {
    "feedback": {
      "id": 12,
      "id_user": 5,
      "customer_name": "Budi Santoso",
      "kriteria": "Kurang",
      "status": "Belum Dibalas",
      "created_at": "2026-06-20 10:00:00"
    },
    "messages": [
      {
        "id": "initial-12",
        "feedback_id": 12,
        "sender_type": "customer",
        "sender_id": 5,
        "sender_name": "Budi Santoso",
        "message": "Tenda yang saya sewa datangnya lambat, pls dibenahi ya.",
        "created_at": "2026-06-20 10:00:00",
        "is_initial": true
      },
      {
        "id": 33,
        "feedback_id": 12,
        "sender_id": 1,
        "sender_type": "admin",
        "sender_name": "Admin KampSewa",
        "message": "Mohon maaf atas ketidaknyamanannya, sedang kami cek.",
        "read_at": "2026-06-20 11:00:00",
        "created_at": "2026-06-20 11:00:00"
      }
    ]
  }
}
```

**⚠️ CATATAN PENTING (wajib dibaca Tim Frontend):**

1. **Pesan pertama itu "synthetic".** Isi `feedback.deskripsi` dikirim sebagai pesan dengan `id` berawalan-teks `"initial-12"` (string, bukan angka) dan flag `is_initial: true`. Kalian **tidak perlu** membuat feedback lalu mengambil pesan ulang — cukup pakai `id` dari response `POST /api/feedback`.
2. **Format tanggal tidak seragam.**
   - Endpoint **list & create** (`/api/feedback`) → format ISO-8601, contoh `2026-06-20T10:00:00.000000Z`
   - Endpoint **messages** (`/api/feedback/{id}/messages`) → format SQL, contoh `2026-06-20 10:00:00`
   - Mohon jangan pakai satu parser tanggal untuk keduanya. Kami sarankan kirim `DateTime.parse()` / `DateFormat.parse()` di sisi Flutter, atau minta backend kami samakan. **Sebutkan pilihan kalian di bagian 8.**
3. **Endpoint ini sekaligus menandai pesan sebagai "dibaca" (side effect).** Setiap kali kalian memanggil `GET messages`, semua pesan dari pihak lawan yang `read_at = null` akan otomatis di-*update* jadi terbaca. Jadi:
   - Jangan panggil endpoint ini hanya untuk cek badge unread.
   - Jangan panggil terlalu sering (lihat bagian 6 tentang polling).
4. **Tidak ada pagination.** Semua pesan dalam 1 feedback dikirim sekaligus. Untuk chat yang sangat panjang, payload bisa besar — mohon sampaikan jika kalian butuh `?last_id=` / pagination.

### 3.4 `POST /api/feedback/{id}/messages` — Kirim Pesan Chat

- Bisa dipanggil oleh **Customer** (`type=0` → tersimpan sebagai `sender_type: customer`) maupun **Admin/Developer** (`type=1` → tersimpan sebagai `sender_type: admin`).

**Body (JSON):**
```json
{
  "message": "Halo Pak, apakah sudah ada kabar soal tenda saya?"
}
```

| Field | Wajib | Keterangan |
|---|---|---|
| `message` | Ya | Maksimal **1000 karakter** |

**Response (201 Created):**
```json
{
  "success": true,
  "message": "Pesan berhasil dikirim.",
  "data": {
    "id": 41,
    "feedback_id": 12,
    "sender_id": 5,
    "sender_type": "customer",
    "sender_name": "Budi Santoso",
    "message": "Halo Pak, apakah sudah ada kabar soal tenda saya?",
    "read_at": null,
    "created_at": "2026-06-22 09:30:00"
  }
}
```

**Efek samping otomatis (tidak perlu dikirim dari mobile):**
- Kalau pengirimnya **Admin**, maka `status` feedback otomatis berubah jadi `Dibalas`, dan semua pesan Customer yang belum dibaca ditandai terbaca.
- Kalau pengirimnya **Customer**, pesan baru berstatus belum dibaca → Admin melihatnya di daftar "Customer Membalas Lagi".

**Response Error:**
```json
// 422
{ "success": false, "message": "Validasi gagal.", "errors": { "message": ["Pesan maksimal 1000 karakter."] } }

// 401 – token tidak ada / kadaluarsa
{ "message": "Unauthenticated." }

// 403 – feedback milik orang lain
{ "success": false, "message": "Anda tidak memiliki akses ke feedback ini." }

// 404 – id feedback tidak ada
{ "message": "No query results for model [App\\Models\\Feedback] 999" }
```

## 3.5 ⚠️ Profil & Foto Pengirim (Avatar) — BELUM TERSEDIA

Ini adalah pertanyaan yang sering ditanyakan: *"Apakah Mobile bisa mengambil data chat dari Admin, lalu menampilkannya seperti chat pada umumnya — ada foto, nama, avatar di tiap bubble?"*

### Jawaban singkat

| Yang dibutuhkan | Status | Keterangan |
|---|---|---|
| Pesan/chat dari Admin | ✅ **Bisa** | `sender_type: "admin"` sudah dikirim di `GET /api/feedback/{id}/messages` |
| **Nama** Admin | ✅ **Sudah ada** | Field `sender_name` sudah tersedia di setiap pesan |
| **Foto / Avatar** Admin | ❌ **Belum ada** | Tidak dikirim di response |
| **Objek profil Admin** di header halaman chat | ❌ **Belum ada** | Response `feedback` hanya berisi `customer_name`, tidak ada data admin |

### Kenapa fotonya belum ada?

Secara teknis datanya **sudah ada** di database (kolom `users.foto`). Pada `app/Http/Controllers/Api/FeedbackChatController.php:243-257`, method `formatMessage()` memang sudah mem-*load* relasi `sender` yang lengkap dengan `foto`-nya, **tetapi objek tersebut dibuang** — yang dikembalikan ke Mobile hanya `sender_name`.

Sebagai informasi, versi **web** pun sama — **belum ada avatar di bubble chat**. Jadi permintaan ini adalah **request baru**, bukan sekadar meniru fitur yang sudah ada.

### Workaround sementara (sudah bisa dipakai, tapi tidak ideal)

Mobile bisa memanggil `GET /api/user/{sender_id}` (`UserController::detailUser`) yang **sudah** mengembalikan `foto`. Kekurangannya:

- Perlu 1 request **per admin** (boros kuota & lambat)
- Kalau admin berganti-ganti pengirim, jumlah request makin banyak
- Tidak scalable untuk list banyak percakapan

### Yang perlu kami kerjakan di Backend (perkiraan ~1 jam)

| No | Perubahan | Dampak |
|---|---|---|
| 1 | Tambah field `sender_foto` di `formatMessage()` | Tiap bubble pesan punya avatar |
| 2 | Tambah objek `admin` di level `feedback` (data admin yang terakhir membalas) | Untuk header halaman chat (nama + foto lawan bicara) |
| 3 | *(Opsional)* `GET /api/feedback/{id}/admin-profile` | Ambil data admin sekali aja per percakapan, lebih hemat request |

### ⚠️ Catatan Penting: Tidak Ada Konsep "Satu Admin Tunggal"

Setiap pesan punya `sender_id`-nya sendiri, dan **bisa ada banyak akun admin/developer (`type = 1`)** yang membalas percakapan berbeda. Artinya:

- **Tidak ada** satu profil admin global yang bisa ditaruh di config aplikasi.
- Profil admin harus diambil **per pengirim pesan** (atau per percakapan, untuk admin terakhir).
- Bisa juga berbeda-beda — **Customer yang berbeda bisa saja dilayani admin yang berbeda**, tergantung siapa yang online.

Konsekuensi ke desain UI Mobile: halaman chat **tidak bisa** memakai avatar statis yang hard-coded. Avatar harus diambil dari data per percakapan/per pesan.

**Mohon konfirmasi di Bagian 8 (Blok A, pertanyaan 8 & 9).**

## 6. ⚠️ PENTING: Fitur Realtime (Realtime/Push) BELUM AKTIF

Backend sudah menyiapkan **event broadcast** (`FeedbackMessageSent`) dengan channel:
- `feedback.admin`
- `feedback.thread.{id_feedback}`

**TAPI:**
- `.env` saat ini masih `BROADCAST_DRIVER=log` (broadcast hanya ditulis ke log, tidak terkirim).
- Library Reverb/Pusher **sudah ter-*install*** di `composer.json`, tapi server Reverb **belum dijalankan**.
- Endpoint autentikasi channel (`/broadcasting/auth`) sekarang hanya memakai **session cookie web**, sehingga **tidak bisa dipakai oleh aplikasi mobile** dengan Bearer Token.
- Di versi web, chat yang "real-time" sekarang sebenarnya **memakai polling tiap 5 detik** (`setInterval` → `GET messages`).

### Implikasi untuk Mobile

> **Untuk saat ini, mohon Mobile TIDAK mengandalkan websocket/push.** Gunakan **polling**.

Rekomendasi polling dari kami:

| Skenario | Interval | Endpoint | Catatan |
|---|---|---|---|
| Chat screen sedang terbuka | **3–5 detik** | `GET /api/feedback/{id}/messages` | Harus dedupe pesan yang sudah dirender (pakai `id` pesan sebagai key). **PENTING:** `initial-12` juga harus masuk key set agar tidak dobel |
| List chat / inbox | **10–15 detik** | `GET /api/feedback` | Badge unread ikut ter-update |
| Background / app ditutup | **jangan polling** | — | Baterai & kuota. Notifikasi saat app tertutup **belum tersedia** (bagian 8) |

**Rate limit API = 60 request/menit.** Polling 3 detik = 20 req/menit (masalah). Polling 5 detik = 12 req/menit. **Disarankan pakai 5 detik + Exponential Backoff** saat koneksi lambat/error.

> **Mohon konfirmasi:** Apakah Mobile ingin **Realtime sungguhan (Reverb/Pusher) dengan FCM push**, atau **cukup polling**? Ini menentukan berapa banyak pekerjaan backend yang perlu kami kerjakan. Jawab di bagian 8.

# Report Permintaan: Perubahan Arsitektur Multi-Admin Chat

**Tanggal:** 29 September 2026
**Kepada:** Tim Backend
**Dari:** Tim Frontend / Mobile
**Perihal:** Permintaan Restrukturisasi Relasi Feedback & Chat Multi-Admin

Halo Tim Backend,

Saat ini kami menemukan sebuah isu kritikal pada pengalaman *Customer* di aplikasi Mobile ketika sebuah feedback dibalas oleh lebih dari satu admin. 

### Akar Masalah:
Secara arsitektur saat ini, semua balasan (dari berbagai admin) disatukan ke dalam satu \eedback_id\ yang sama di dalam tabel \eedback_messages\. Akibatnya, ketika Admin B ikut membalas, Mobile (yang mengambil \last_admin_name\) akan seketika menimpa nama Admin A menjadi Admin B. Percakapan menjadi campur aduk dan membingungkan *Customer*.

### Kebutuhan (Solusi yang Diharapkan):
*Customer* seharusnya melihat **2 chat/room yang terpisah** jika ada 2 admin yang berbeda merespons feedback yang sama.

Untuk mengakomodasi ini, kami mengusulkan perubahan di sisi Backend:

1. **Pembuatan Konsep \Room Chat\ / \Thread\**:
   Satu Feedback (dari Customer) bisa memiliki banyak *Room* (satu *room* per Admin yang merespons).
   - Tabel \eedback_messages\ perlu ditambahkan kolom \dmin_id\ (atau \oom_id\), sehingga pesan dari *Customer* bisa terhubung ke obrolan dengan *Admin* yang tepat.

2. **Perubahan API \GET /api/feedback\ (List Chat)**:
   List API tidak lagi sekadar mengembalikan list *Feedback*, melainkan **List Room Chat**. Jika ada 2 admin membalas 1 feedback, API list harus mengembalikan 2 objek *room* yang berbeda (misalnya \Chat dengan Admin A\ dan \Chat dengan Admin B\).

3. **Perubahan API \GET /api/feedback/{id}/messages\**:
   API *detail message* tidak bisa lagi hanya memakai \eedback_id\. Kami butuh parameter tambahan, misal \GET /api/chat-room/{room_id}/messages\, agar Mobile hanya me-*render* pesan antara *Customer* tersebut dengan satu *Admin* tertentu.

**Catatan Tambahan**:
Untuk sementara waktu, sebagai *quick fix*, fitur chat di **sisi Admin Web** sudah difilter agar setiap Admin **hanya** melihat chat dari *Customer* dan pesan dari dirinya sendiri (balasan dari Admin lain disembunyikan dari layar miliknya).

Mohon segera direview dan diagendakan untuk perubahan skema database ini agar kami bisa menyesuaikan *UI Mobile* secepatnya.

Terima kasih.
